# unplugin-deno — Frameworks, real-world usage & demand research

*Research date: 2026-09-25 (local toolchain: Deno 2.9.7, Node 26). Scope: the **consumer / demand side** — how frameworks and users bundle Deno code today, what breaks, and what a best-in-class multi-bundler Deno plugin must do. Plugin internals (`@deno/vite-plugin`, `@deno/loader`, `@luca/esbuild-deno-loader`, …) are covered by other agents and only referenced here where needed for the "who already does this" column.*

Raw data (issue JSON dumps, issue bodies) lives in `$SCRATCH/data/demand/` (`issues/*.txt` = full issue bodies + comments). Framework sub-reports: `$SCRATCH/research/frameworks-A.md` (Astro, SvelteKit, Nuxt/Nitro, Remix/React Router, TanStack Start, SolidStart, Qwik) and `$SCRATCH/research/frameworks-B.md` (Lume, Hono+Vite, Ultra, Aleph, Lockness, deno-plc, Vike, misc).

---

## 0. TL;DR

1. **No single official setup.** Deno's docs Vite tutorial = `create-vite` + package.json + `deno install` + plain Vite (no Deno plugin, Node resolution via `node_modules`; docs recommend `nodeModulesDir: "manual"` for Vite/framework projects). Deno's React/Vue tutorials and the `create-vite-extra` `deno-*` templates = deno.json + `--node-modules-dir` + **`@deno/vite-plugin`** (2.0.4, ~10.4k npm downloads/week, Vite-only, built on `@deno/loader`, README: cannot help `vite.config.ts`). Fresh 2 = its **own** Vite plugin on `@deno/loader` (Vite 7, `nodeModulesDir: "manual"`). JSR docs = use JSR's npm-compat registry, no Deno resolution. `deno bundle` (esbuild, no plugin API yet; PR #34345 would add Rolldown + plugins) is positioned for small apps only. The Deno team explicitly pushes bundler-resolution work into plugins; platform helpers that landed in 2026: opt-in `jsrDepsInNodeModules` (2.9, [#35029](https://github.com/denoland/deno/pull/35029)), `deno info --json` `npmPackages[*].localPath` (2.8.3, [#34806](https://github.com/denoland/deno/pull/34806)), Node `module.registerHooks` (sync only; `format` not populated — [#36841](https://github.com/denoland/deno/issues/36841)).
2. **How frameworks really do it:** mainstream meta-frameworks (Astro, SvelteKit, Nuxt/Nitro, React Router, TanStack Start, SolidStart, Qwik, Vike, Hono) **ship no Deno resolver** — they rely on package.json/`npm:` deps installed into `node_modules`; `jsr:`/`npm:` in source are unsupported without `@deno/vite-plugin` (which breaks on framework `virtual:` ids). Deno-native: **Fresh** (own `@deno/loader` Vite plugin, forces `ssr.noExternal: true`, disables prebundling, Babel CJS/env/JSX patches; blocked on Vite 8; maintenance slowed) and **Lume** (esbuild + own plugin over `@deno/loader`, server unbundled). Lockness/deno-plc roll their own `deno info` resolvers; Ultra/Aleph are dead.
3. **Deno Deploy** runs install/build commands under Deno (even `node`/`npm` are Deno shims), caches `DENO_DIR`, and imposes 5-min / 3-GB build defaults and `--cached-only`, flag-less runtime — so plugin speed, static externals and DENO_DIR reuse matter. `deno desktop` (2.9) now also loads Vite configs inside its runtime.
4. **Top demand themes** (≈545 deno issues + ~1,000 Fresh issues + plugin/bundler trackers screened): SSR/CJS/externals (~30), Deno resolution missing in bundlers (~25), workspaces (~24), plugin interop (~24), Windows (~18), Vite 8/Rolldown (~16), Tailwind/CSS (~15), lock/cache/registries (~14), non-Vite bundlers (~14), env/defines (~13), performance (~11), sourcemaps (~11).
5. **Nobody provides:** one plugin for all bundlers (asked in deno-vite-plugin#34), an SSR "externalize-to-Deno" mode with sane CJS interop, config-file resolution, generic env/`Deno.env` inlining, browser-safety diagnostics, deno.json-only framework support (vitefu lists), bridging JSR to Tailwind/PostCSS/tsc, dedupe enforcement, DENO_DIR-aware sourcemaps, `server.fs.allow`/workspace-root fixes.
6. **Avoid:** subprocess-per-import (`deno info`) and unbounded concurrency (OOM), Deno-binary/`--allow-run` requirements, greedy resolution that eats `?query`/`virtual:`/`\0` ids, silent externalization/fallbacks, cryptic errors, global config hijacking (`noExternal: true`, no optimizeDeps), Babel-on-every-file, framework-specific JSX assumptions, lagging bundler majors, no Windows CI.
7. **Naming:** npm `unplugin-deno` is **free**; JSR has `@jeiea/unplugin-deno` (0.1.1, one-day project from 2025-03-27, 0★, https-only Rolldown resolver, abandoned though the author is active elsewhere). No published Deno trademark naming policy; nominative "*-deno" names are common (`@astrojs/deno`, `@sentry/deno`…); avoid the `@deno/` scope, logo, and "official" wording, add a non-affiliation note.

## 1. What is "officially recommended" today (Sept 2026)

There is **no single blessed setup**. Several official or semi-official answers co-exist, and they contradict each other:

No plugin API as of 2.9.7 — open PR [denoland/deno#34345](https://github.com/denoland/deno/pull/34345) (2026-05-25, unmerged) swaps the backend to Rolldown 1.2 and adds `Deno.bundle({ plugins })` ([#32157](https://github.com/denoland/deno/issues/32157) asks for Bun-style plugins; a commenter asks why esbuild's plugin API is not exposed through `Deno.bundle`). |

Other official references to Deno bundler plugins in docs: Cloudflare Workers tutorial uses `jsr:@deno/esbuild-plugin` (`examples/tutorials/cloudflare_workers_wrangler.md`); migration guide still points at `jsr:@luca/esbuild-deno-loader` (`runtime/reference/migration_guide.md`). `deno create npm:vite` / `deno init --npm vite` simply run `create-vite`, whose templates contain a plain `vite.config.ts` (`plugins: [react()]`, no Deno plugin) and a package.json.

**Deno core team's stated position (June 2026):** when closing the long-standing "JSR in Vite" issues, bartlomieju wrote that `@deno/vite-plugin` "covers the original request", and that follow-ups about faster resolution (a programmatic resolver instead of `deno info` per import) belong in the plugin tracker — "that work lives in the plugin rather than in the CLI" ([#23929](https://github.com/denoland/deno/issues/23929), [#26492](https://github.com/denoland/deno/issues/26492)). Bundler-native resolvers (Rolldown/OXC) ignoring import maps is explicitly "not something Deno can fix on its side" ([#33787](https://github.com/denoland/deno/issues/33787)). Deno also rejected a bespoke `Deno.Loader` API in favour of Node's `module.registerHooks` ([#30864](https://github.com/denoland/deno/issues/30864), [#31665](https://github.com/denoland/deno/issues/31665)) — which still has gaps (`format` never populated [#36841](https://github.com/denoland/deno/issues/36841); `.node` addons compiled as JS under load hooks [#36240](https://github.com/denoland/deno/issues/36240); async `module.register()` unsupported).

**Implication for unplugin-deno:** the ecosystem has converged on "Vite (+ Node-style `node_modules`) run by Deno", with Deno-specific resolution bolted on by a Vite-only plugin. Everything *outside* Vite (Rolldown standalone, esbuild, rspack/webpack, Rollup, farm, Bun) is served by fragmented, mostly single-maintainer plugins.

## 2. Frameworks & meta-frameworks

### 2.1 Fresh 2.x (freshframework/fresh, formerly denoland/fresh) — deep dive

* **Status:** 13.8k★, 158 open issues; repo moved to the `freshframework` org and docs to usefresh.dev; latest release `@fresh/core` 2.3.3 (2026-04-28); last commit on `main` 2026-06-03 (fixes merged in May are unreleased; docs mention a "Fresh 2.4"). Vite 8 support is still an open tracking issue — maintenance has visibly slowed.
* **Bundler:** Vite 7 (Environments API: `client` + `ssr`), `@fresh/plugin-vite` 1.1.2 (JSR). Fresh 2.0 beta with Vite announced 2025-09-02 (https://deno.com/blog/fresh-and-vite): HMR is limited to island code (server-only edits trigger a full reload); server code is bundled for 9–12× faster production boot.
* **Deno resolution:** Fresh does **not** use `@deno/vite-plugin`. It ships its own `deno()` Vite plugin (`packages/plugin-vite/src/plugins/deno.ts`, ~420 LOC) built on `jsr:@deno/loader@^0.4`:
  * two loaders: `new Workspace({ platform: "node", cachedOnly: true })` for SSR and `new Workspace({ platform: "browser", preserveJsx: true, cachedOnly: true })` for the client (`// TODO: Pass conditions`). `cachedOnly: true` ⇒ **requires a prior `deno install`**; transient deps missing → "Cannot find module 'npm:marked-footnote@^1.2'" ([fresh#3467](https://github.com/freshframework/fresh/issues/3467)).
  * `enforce: "pre"` — per the source comment it must run before Vite's own `vite:resolve`, which treats bare specifiers as external during SSR. It calls `this.resolve()` first and ignores results from `vite:resolve` (relies on `resolvedBy`, which **Rolldown does not support** — [fresh#3777](https://github.com/freshframework/fresh/issues/3777), [rolldown#8688](https://github.com/rolldown/rolldown/issues/8688)).
  * Remote modules (`jsr:`/`npm:`/`https:` results) become virtual ids `\0deno::<type>::<specifier>`; import attributes (`json`/`text`/`bytes`) mapped to `RequestedModuleType` (Rolldown lacks import-attribute support in hooks — [rolldown#2758](https://github.com/rolldown/rolldown/issues/2758)).
  * JSX in remote/local TSX is transformed with **Babel** (`@babel/preset-react`, preact hard-coded); SSR re-uses Deno's `precompile` JSX transform via a transform "hack" that reloads the file through the loader.
  * Only enabled when `process.versions.deno` is set — i.e. Fresh does **not** work when Vite runs on Node ([fresh#3284](https://github.com/freshframework/fresh/issues/3284) "Get Fresh working in Node" — JSR's npm tarball for `@fresh/core` lacks compiled `.tsx`).
* **Config it forces on Vite:** `resolve.noExternal: true` (source comment: externals produced duplicate `preact` vs `npm:preact@*` instances), `optimizeDeps.noDiscovery: true` (comment: prebundling produced duplicate modules / wrong chunks), react→preact/compat aliases, watcher ignores for temp files (Deno `watchFs` race), `.env*` loading.
* **Babel "patches" plugin on every JS file** (`plugins/patches/*`): a ~960-line CJS→ESM transform (because externals & prebundling are off), `Deno.env.get("FRESH_PUBLIC_*")`/`process.env.*`/`import.meta.env.*` inlining, dead-branch evaluation (`IS_BROWSER`-style), polyfill stripping, JSX comment fix, `http_absolute` (rewrites root-relative imports inside `https:` modules). Plus `verify_imports.ts`: errors when Node built-ins reach the client ("Node built-in modules cannot be imported in the browser.") — the only framework-level browser-safety check found.
* **What breaks (Fresh 2 era issues):**
  * **npm packages (mostly CJS) in SSR** — the #1 Fresh complaint: `@supabase/postgres-js` ([#3449](https://github.com/freshframework/fresh/issues/3449)), `qs`/stripe ([#3492](https://github.com/freshframework/fresh/issues/3492), [#3565](https://github.com/freshframework/fresh/issues/3565)), `@google-cloud/storage` ([#3611](https://github.com/freshframework/fresh/issues/3611)), mongoose ([#3505](https://github.com/freshframework/fresh/issues/3505)), mongodb ([#3478](https://github.com/freshframework/fresh/issues/3478), [#3362](https://github.com/freshframework/fresh/issues/3362)), redis ([#3480](https://github.com/freshframework/fresh/issues/3480)), ioredis ([#3673](https://github.com/freshframework/fresh/issues/3673)), pg ([#3323](https://github.com/freshframework/fresh/issues/3323)), cloudflare SDK ([#3549](https://github.com/freshframework/fresh/issues/3549)), `@opentelemetry/api` "exports is not defined" in a *fresh scaffold* ([#3794](https://github.com/freshframework/fresh/issues/3794)), `require is not defined` ([#3520](https://github.com/freshframework/fresh/issues/3520), [#3619](https://github.com/freshframework/fresh/issues/3619)), sharp works in dev but fails after build ([#3653](https://github.com/freshframework/fresh/issues/3653): "it would be awesome if … could issue a warning when encountering CJS"), libsql native binary missing in prod ([#3593](https://github.com/freshframework/fresh/issues/3593)), `@react-email/components` build fails ([#3579](https://github.com/freshframework/fresh/issues/3579)). Maintainers now want to replace Babel CJS with a cjs-module-lexer/deno_ast-based transform ([#3800](https://github.com/freshframework/fresh/issues/3800)).
  * **SSR can't let Deno handle its own imports:** `ssr.external: ["mongodb-deno"]` (import-map alias → `jsr:@db/mongo`) is ignored; direct `jsr:` fails; custom "mark jsr: external" plugin "Breaks Fresh's own JSR dependencies" ([#3654](https://github.com/freshframework/fresh/issues/3654)).
  * **Vite features vs Deno resolution:** `?raw` ignored when the path goes through a deno.json alias ([#3893](https://github.com/freshframework/fresh/issues/3893)), `?worker&url` passed verbatim into the Deno loader ([#3412](https://github.com/freshframework/fresh/issues/3412)), `optimizeDeps` → `?v=hash` ids percent-encoded into file URLs → ENOENT ([#3895](https://github.com/freshframework/fresh/issues/3895)), `.wasm` from `jsr:@deno/doc` not handled ([#3897](https://github.com/freshframework/fresh/issues/3897)), `browser: { "./x.js": false }` field not honored by `@deno/loader` ([#3546](https://github.com/freshframework/fresh/issues/3546) → [deno-js-loader#66](https://github.com/denoland/deno-js-loader/issues/66)), fonts from `node_modules` in dev ([#3424](https://github.com/freshframework/fresh/issues/3424)), `node:module` from framer-motion in client ([#3429](https://github.com/freshframework/fresh/issues/3429)), `crypto` in client ([#3063](https://github.com/freshframework/fresh/issues/3063)), vanilla-extract ([#3392](https://github.com/freshframework/fresh/issues/3392)), `@cloudflare/vite-plugin` ([#3771](https://github.com/freshframework/fresh/issues/3771)), Cloudflare Workers deploy ([#3402](https://github.com/freshframework/fresh/issues/3402)), `server.proxy` ([#3814](https://github.com/freshframework/fresh/issues/3814)).
  * **Vite 8 / Rolldown blocked** ([#3777](https://github.com/freshframework/fresh/issues/3777) +4, [#3694](https://github.com/freshframework/fresh/issues/3694) +4): Vite 8 needs `node:util.parseEnv` (Deno ≥2.7), **`vite --configLoader=native`** is required or `@fresh/plugin-vite` "Could not resolve … treating it as an external dependency" in `vite.config.ts`; `.cjs` transformed to ESM then parsed as CJS; `resolvedBy` unsupported; import attributes unsupported.
  * **Duplicates:** islands dead because two preact copies (Deno < 2.7.5 peer-dep install bug) — [denoland/deno#30687](https://github.com/denoland/deno/issues/30687), [fresh#3599](https://github.com/freshframework/fresh/issues/3599), [#2973](https://github.com/freshframework/fresh/issues/2973); the Fresh troubleshooting doc tells users to stop using esm.sh because it causes duplicate Preact copies.
  * **Windows:** constant rebuilds ([#3637](https://github.com/freshframework/fresh/issues/3637)), Windows-built output embeds `client\\assets\\…` paths that break on Linux ([#3651](https://github.com/freshframework/fresh/issues/3651)).
  * **Debuggability/perf:** wrong line numbers ([#3609](https://github.com/freshframework/fresh/issues/3609)), SSR sourcemaps ([#3826](https://github.com/freshframework/fresh/issues/3826)), "no reliable way to debug server-side application code in Fresh 2" ([#3670](https://github.com/freshframework/fresh/issues/3670) +4), minutes to first interactive page in dev ([#3821](https://github.com/freshframework/fresh/issues/3821)), no hook filters ([#3331](https://github.com/freshframework/fresh/issues/3331), Rolldown team asked for them), "Can Fresh be without Vite?" ([#3668](https://github.com/freshframework/fresh/issues/3668)).
  * **Workspaces:** glob members break `@deno/loader`/esbuild plugins ([#3805](https://github.com/freshframework/fresh/issues/3805)); `nodeModulesDir: "auto"` broke workspace layout ([#3019](https://github.com/freshframework/fresh/issues/3019)); Tailwind can't resolve `tailwindcss` in a monorepo ([#3499](https://github.com/freshframework/fresh/issues/3499)).
* **Takeaway:** Fresh is the most sophisticated consumer and a **reference implementation of what a framework needs from a Deno plugin** (two platform loaders, virtual ids for remote modules, JSX for remote TSX, CJS interop, env inlining, browser-safety checks) — but it hard-codes Preact/Babel, only runs on Deno, disables Vite's prebundling & externals, and is blocked on Vite 8. A framework-agnostic `unplugin-deno` that Fresh could *adopt* (instead of maintaining `plugins/deno.ts` + patches) is a credible positioning target.

### 2.2 Lume (lumeland/lume) — the reference *esbuild* consumer

* 2,283★, v3.3.2 (2026-09-22), very active. Client code bundled by `npm:esbuild@0.28.2` inside Lume's own esbuild plugin **`lume-loader`** (`deps/esbuild-loader/loader.ts`, ~260 LOC) wrapping **`jsr:@deno/loader@0.5.0`** (`new Workspace({ configPath, nodeConditions, platform })` → `loader.resolve/load`). Server/SSR is *not* bundled — Deno runs `_config.ts`, pages and JSX natively.
* History = the whole ecosystem's history: Lume ≤2 rewrote `npm:`/`jsr:` to **esm.sh** URLs (bugs [#706](https://github.com/lumeland/lume/issues/706), [#444](https://github.com/lumeland/lume/issues/444)); v3.0.0 (2025-05) moved to `@luca/esbuild-deno-loader@0.11.1` (CJS `require('./data')` in npm pkg broke — [#751](https://github.com/lumeland/lume/issues/751)); v3.0.6 (2025-08) moved to `@deno/loader`; v3.2.5 had to force `platform: "browser"`; Windows `Received protocol 'c'` ([#808](https://github.com/lumeland/lume/issues/808)).
* Lume-specific needs worth copying: in-memory/virtual entry files; `alias` option; Node built-ins → external + warning; esbuild `external` globs; JSON imported without `with {type:"json"}` forced to JSON; JSX config read from deno.json; **a separate `denoConfig` (import map + JSX runtime) for browser code** — the maintainer's main reason not to adopt `Deno.bundle` (no custom loader/virtual files, no separate import map/JSX — [#795](https://github.com/lumeland/lume/issues/795)). Docs advise registering all npm/jsr deps in the import map because inline `npm:x@ver` imports make CI builds try to write to the Deno cache.


### 2.3 Mainstream meta-frameworks on Deno (details: `frameworks-A.md`)

**Headline: no mainstream meta-framework ships a Deno resolver.** They all run on Deno via Node compatibility — deps in `package.json` (or `npm:` entries in deno.json), a real `node_modules` (`nodeModulesDir: auto|manual` + `deno install`), and the bundler's normal Node resolution. Vite 8.3.1 treats `npm:x`/`jsr:@s/x` as bare package names (its `bareImportRE`), so they fail unless a Deno plugin is added; "JSR support" in these ecosystems means JSR's npm-compat registry. Deno's own tutorials for Astro, SvelteKit, Svelte, Nuxt, Qwik and Solid do **not** use `@deno/vite-plugin` (only the plain React/Vue SPA tutorials do).

**Cross-cutting lessons from these frameworks (for the plugin):**
* **`package.json` is load-bearing even on Deno**: vitefu (`crawlFrameworkPkgs`, used by vite-plugin-svelte and vite-plugin-solid), SvelteKit `adapter-node`, React Router, Qwik derive `ssr.noExternal`/optimizeDeps/externals from package.json — deno.json-only projects break in framework-specific ways (Astro #67, solid-start #1990, kit #14555, qwik #8616). Workarounds: stub package.json or manual `ssr.noExternal`. ⇒ A plugin can **synthesize these lists from deno.json imports/lockfile**.
* **Build-time vs runtime conditions differ** (Vite SSR resolves with `node`; Deno runs with `deno`+`node`) — react-dom/server, srvx, Nitro dev. ⇒ Add `deno` to SSR `resolve.conditions`/`externalConditions` when the output runs on Deno.
* **Three SSR output strategies exist** (keep bare externals / bundle everything / Deno-scheme externals); only the Astro adapter's own `jsr:@std` imports and Nitro's legacy `npm:` rewrite use Deno schemes today. Deno Deploy's `--cached-only` requires such externals to be **static** imports.
* **Virtual modules must be deferred to their owners**: call `this.resolve(..., { skipSelf: true })` first and skip `\0`, `virtual:`, `astro:`, `$app/*`, `$env/*`, `#imports`, `~/`, `?query` ids (Fresh's pattern; fixes dvp#101/#36).
* **Official Deno templates are shrinking** (React Router dropped its Deno template; SvelteKit declined deno.json-only; Astro declined config aliases) — frameworks expect the Deno side (plugins/adapters) to adapt to them.

### 2.5 Deno Deploy (the new "EA" platform, now just "Deno Deploy") — build pipeline

Source: `deploy/reference/builds.md` (2026-08-04), `deploy/reference/frameworks.md` (2026-07-07), `deploy/reference/runtime.md` in https://github.com/denoland/docs (rendered at https://docs.deno.com/deploy/reference/builds/ etc.).

* **Stages:** Queuing → Preparing (download source, **restore build caches**) → **Install** command (e.g. `deno install`, `npm install`) → **Build** command (e.g. `deno task build` / `npm run build`) → Deploy (per-timeline DB, **pre-deploy** command, warm-up in Preview, routing). Build caching "happens automatically for framework presets and the `DENO_DIR` dependency cache".
* **Everything runs on Deno:** all JavaScript in the builder runs on Deno; `node` is a shim over `deno run`, and `npm`/`npx`/`yarn`/`pnpm` also run through Deno. ⇒ even a "Node" Vite config runs under Deno on Deploy; a plugin must behave identically when `process.versions.deno` is set and a Deno binary is on PATH. Tools available: `deno`, `node`(shim), `npm`, `npx`, `yarn` v1, `pnpm`, `git`, `tar`, `gzip`.
* **Limits that matter for plugin design:** build timeout **5 min** default (15 on Pro); build memory **3 GB** default (4 GB Pro). ⇒ a plugin that spawns a `deno info` per import can blow both (compare [deno-vite-plugin#50](https://github.com/denoland/deno-vite-plugin/issues/50): ">8GB of memory pressure … kills the build", build 2.4 s → 20 s).
* **Config from source:** `deno.json` `"deploy": { framework | install | build | predeploy | runtime: { type: dynamic|static, entrypoint, args, cwd, spa, memory_limit } }`. Env vars: only the "Build" context is visible during builds; `CI=true`, `DENO_DEPLOY=true`, `DENO_DEPLOY_ORG_ID`, … are set.
* **Framework presets (auto-detected):** `nextjs`, `astro` (SSR needs `@deno/astro-adapter`), `nuxt` and `solidstart` and `tanstackstart` ("Deno Deploy automatically configures Nitro"; TanStack Start needs the `nitro` Vite plugin), `sveltekit` ("requires no additional setup"), `fresh`, `lume`, `remix` (experimental). Changelog (2025-06-24): framework auto-detection extended to many Vite-based projects; an earlier changelog entry fixed `npm install` failing to install `esbuild`.
* **Runtime:** standard Deno runtime with `--allow-all`; "Custom flags, including `--unstable-*` flags, cannot be passed" (so e.g. `Deno.bundle()` — behind `--unstable-bundle` — is not usable at request time). Docs claim runtime is Deno 2.5.0 (probably stale). Cold-start advice: minimise deps, lazy `import()`; the platform profiles file access during warm-up.
* **No bundler/plugin constraints are documented** — any bundler that runs under Deno works. The practical constraints are time/memory, the Deno-shimmed `node`, `DENO_DIR` caching (a plugin should reuse the DENO_DIR cache rather than a private cache dir, so it benefits from Deploy's cache restore), and `deno.lock`/frozen installs.
* Related pain: [fresh#3694](https://github.com/freshframework/fresh/issues/3694) — Vite 8 build failed *on Deno Deploy* (`node:util.parseEnv` missing) → users pin Vite 7; [denoland/deno#36148](https://github.com/denoland/deno/issues/36148) Fresh/Vite build fails only in GitHub Actions (the reporter says the recommended Deno Vite plugin made the build fail locally as well).

### 2.6 `deno desktop` (Deno 2.9) — a brand-new Vite consumer

`deno desktop` (docs `runtime/desktop/frameworks.md`, 2026-06-27) auto-detects Next.js, Astro, Fresh, Remix, React Router, Nuxt, SvelteKit, SolidStart, TanStack Start and plain **Vite** (`vite.config.*` or `vite` dep; SSR if a `server.{ts,js,mjs}` sits next to it), embeds the build output in a binary and runs the framework's dev server under `--hmr`. This means Vite configs are now also loaded *inside the Desktop runtime*, with its own resolution bugs: transitive npm dep of `@sveltejs/kit` not resolvable while loading `vite.config.ts` ([#36870](https://github.com/denoland/deno/issues/36870)), `--hmr` crashes with Vite 8 ([#36712](https://github.com/denoland/deno/issues/36712)), ignores `deno.json` in framework dir ([#35653](https://github.com/denoland/deno/issues/35653)), SvelteKit/Vue/template-Vite failures ([#35531](https://github.com/denoland/deno/issues/35531), [#35745](https://github.com/denoland/deno/issues/35745), [#35535](https://github.com/denoland/deno/issues/35535), [#35590](https://github.com/denoland/deno/issues/35590)). A plugin should not assume "Deno CLI process == Vite process".

### 3.3 Theme details (with links)

**T1 — Deno resolution missing in bundlers (~25).**
* "JSR in Vite" was the canonical ask for 2 years: [deno#23929](https://github.com/denoland/deno/issues/23929) (+19; users fell back to `npx jsr add` + npm, or esbuild + `@luca/esbuild-deno-loader`; one says Node is still needed just to manage deps), [#26492](https://github.com/denoland/deno/issues/26492) (Vite's SSR `isBuiltin` whitelist knows `npm:` but not `jsr:`; attempted Vite PR [vitejs/vite#18479](https://github.com/vitejs/vite/pull/18479)), [#26319](https://github.com/denoland/deno/issues/26319), [#26569](https://github.com/denoland/deno/issues/26569) (SolidStart: moving deps from package.json to deno.json breaks Vite resolution; `optimizeDeps.include` entries "Failed to resolve"), [#17043](https://github.com/denoland/deno/issues/17043), [#20493](https://github.com/denoland/deno/issues/20493) (asked for `deno resolve` for community bundlers; the requester later abandoned Deno), [#29777](https://github.com/denoland/deno/issues/29777) (core team goal: bundlers must not spawn thousands of subprocesses → `@deno/loader`), [#27862](https://github.com/denoland/deno/issues/27862) (open tracking issue "refactors to support external bundlers").
* JSR packages are **not materialised in `node_modules`** (only `npm:` are), so any Node-resolution tool (tsc, svelte-check, Vite, Tailwind) fails: [deno#33370](https://github.com/denoland/deno/issues/33370) (open; workaround: declare `"@std/ulid": "jsr:^1"` in package.json, or map to `npm:@jsr/std__ulid` — which installs under the wrong name), [deno#26091](https://github.com/denoland/deno/issues/26091) (Rsbuild; maintainer: every bundler has its own resolver and assumes `node_modules`). Partial platform fix: Deno 2.9 merged an **opt-in** `jsrDepsInNodeModules` that installs `jsr:` deps into `node_modules` via the npm-compat registry ([denoland/deno#35029](https://github.com/denoland/deno/pull/35029), merged 2026-06-24) and Deno 2.8.3 added `npmPackages[*].localPath` to `deno info --json` for bundler tooling ([#34806](https://github.com/denoland/deno/pull/34806)) — yet a Sept-2026 commenter on #33370 still hits the Tailwind/JSR case, so discoverability (or alias naming) remains a problem.

## 5. Capabilities NO existing plugin provides (as far as I could find)

1. **One plugin, every bundler, same semantics** — Vite, Rolldown, Rollup, esbuild, webpack, rspack/Rsbuild, farm (and Bun.build via its esbuild-like API). Explicitly requested in [deno-vite-plugin#34](https://github.com/denoland/deno-vite-plugin/issues/34) ("Make this an unplugin?", +3); today each bundler has a different, mostly single-maintainer plugin.
2. **SSR "externalize to Deno" mode** with Node-compatible CJS interop and native-addon policy (Fresh's #1 complaint cluster; §2.1).
3. **Config-file resolution** (`vite.config.ts` etc. importing `jsr:`/aliases) — the official plugin documents this as impossible.
4. **Framework-agnostic env/define inlining** incl. `Deno.env.get` + `import.meta.main` handling (only Fresh does a Preact-specific version).
5. **Generic browser-safety import checks** with import-chain explanations (only Fresh).
6. **Bridging Deno resolution to non-bundler resolvers** (Tailwind/PostCSS/Sass/tsc) — JSR packages aren't in `node_modules` by default ([deno#33370](https://github.com/denoland/deno/issues/33370) open; Deno 2.9's opt-in `jsrDepsInNodeModules` ([#35029](https://github.com/denoland/deno/pull/35029)) helps only if users know about it, and import-map aliases still aren't materialised under their alias names).
7. **Duplicate-instance detection/enforcement** across `npm:`/bare/esm.sh/prebundled copies.
8. **DENO_DIR-aware sourcemaps** (readable `jsr:`/`https:` sources).
9. **Deno-workspace awareness for the bundler itself** (Vite `server.fs.allow`/root from `deno.json` — [vite#22237](https://github.com/vitejs/vite/issues/22237)).
10. **Ambient type generation** for bundler-only imports so Deno LSP stops flagging them.
11. **License/SBOM for `jsr:`/`https:` deps.**
12. **deno.json-only projects in frameworks** — synthesising the package lists frameworks read from package.json (vitefu etc.) so Astro/SvelteKit/SolidStart/Qwik work without a stub package.json.
13. **Works identically when the bundler runs on Node/Bun** (Fresh's plugin is Deno-only; others need a Deno binary) *and* inside `deno desktop`/Deno Deploy's Deno-shimmed `node`.

## 6. Anti-features (things users complained about — avoid)

* **Spawning `deno info` (or any subprocess) per import / unbounded concurrency** → OOM (>8 GB) and 10× slower builds ([dvp#50](https://github.com/denoland/deno-vite-plugin/issues/50), [#55](https://github.com/denoland/deno-vite-plugin/issues/55), [deno#29777](https://github.com/denoland/deno/issues/29777)); requires `--allow-run`.
* **Requiring the Deno binary on PATH / picking the wrong binary** (Windows: [dvp#86](https://github.com/denoland/deno-vite-plugin/issues/86), [#72](https://github.com/denoland/deno-vite-plugin/issues/72)); Deno-only operation ([fresh#3284](https://github.com/freshframework/fresh/issues/3284)).
* **Greedy `enforce: "pre"` resolution that claims ids it doesn't understand** — breaks `?raw`/`?worker`/`?v=`/`virtual:`/`\0` ids and other plugins ([fresh#3893](https://github.com/freshframework/fresh/issues/3893), [#3412](https://github.com/freshframework/fresh/issues/3412), [#3895](https://github.com/freshframework/fresh/issues/3895), [dvp#101](https://github.com/denoland/deno-vite-plugin/issues/101), [dvp#17](https://github.com/denoland/deno-vite-plugin/issues/17)).
* **Silent fallbacks**: swallowing resolution errors (`catch { /* ignore */ }` in Fresh's resolver), letting Vite "externalize for browser compatibility" (`npm:react` — [dvp#40](https://github.com/denoland/deno-vite-plugin/issues/40)), Rolldown "treating it as an external dependency" in config loading ([fresh#3777](https://github.com/freshframework/fresh/issues/3777)), build that passes in dev and fails in prod ([fresh#3653](https://github.com/freshframework/fresh/issues/3653)).
* **Cryptic errors**: `Cannot read properties of undefined (reading '0')` ([dvp#75](https://github.com/denoland/deno-vite-plugin/issues/75)), `Unexpected end of JSON input` ([dvp#38](https://github.com/denoland/deno-vite-plugin/issues/38)), raw Wasm stack traces ([fresh#3412](https://github.com/freshframework/fresh/issues/3412)), Rust panics ([deno-rolldown-plugin#14](https://github.com/denoland/deno-rolldown-plugin/issues/14), [#7](https://github.com/denoland/deno-rolldown-plugin/issues/7)).
* **Global config hijacking**: forcing `ssr.noExternal: true` and disabling `optimizeDeps` for everyone (Fresh) — causes the CJS breakage cluster and slow dev.
* **Heavy per-file Babel transforms** (Fresh's 960-line CJS transform + patches on every JS file — [fresh#3800](https://github.com/freshframework/fresh/issues/3800)); no hook filters ([fresh#3331](https://github.com/freshframework/fresh/issues/3331)).
* **`cachedOnly` without auto-install or a clear "run `deno install`" message** ([fresh#3467](https://github.com/freshframework/fresh/issues/3467)).
* **Framework assumptions** (Preact hard-coded JSX, React-only `optimizeDeps.include: ["react/jsx-runtime"]` copied into Vue docs).
* **Lagging bundler majors** (Fresh pinned to Vite 7; users on Deploy forced to downgrade — [fresh#3694](https://github.com/freshframework/fresh/issues/3694)); **unreviewed critical PRs** ([deno#29727](https://github.com/denoland/deno/issues/29727) escalated because a Windows fix sat for weeks).
* **Stale/abandoned plugins with no Windows CI** (`deno-rolldown-plugin` stalled 2025-07; `@jeiea/unplugin-deno` single-day project; many forks in `$SCRATCH/repos`).
* **Private cache directories / temp-dir renames** that break in CI/Docker ([esbuild_deno_loader#82](https://github.com/lucacasonato/esbuild_deno_loader/issues/82), [#84](https://github.com/lucacasonato/esbuild_deno_loader/issues/84)) instead of reusing `DENO_DIR` (which Deno Deploy caches for you).
* **Bundler-specific APIs baked into the core** (Vite-only `configResolved` prevents reuse in Rollup/Rolldown — noted in [rolldown#3172](https://github.com/rolldown/rolldown/issues/3172)).
* **Silently externalizing Deno specifiers**: webpack ≥5.102's `externalsPresets.web` (default `target: "web"`) externalizes `jsr:`/`npm:` requests, and webpack 5.108's new `target: "deno"` keeps them external without resolving deno.json (per `rolldown-rollup-rspack-webpack.md`) — a plugin must detect and override this, loudly.

## 7. Naming / positioning check

* **npm `unplugin-deno`: available** (`npm view unplugin-deno` → E404 on 2026-09-25). Also free: `deno-unplugin`, `unplugin-deno-resolve`, `@deno/unplugin` (but the `@deno` scope belongs to Deno Land Inc. — don't use it).
* **JSR: `@jeiea/unplugin-deno` exists** — https://jsr.io/@jeiea/unplugin-deno, repo https://github.com/jeiea/unplugin-deno. v0.1.0/0.1.1 both published 2025-03-27, description "Resolve https import with rolldown etc.", README: a "simplified version of `@bureaudouble/rolldown-deno-loader-plugin`", "Not extensively tested", 0 stars, no commits after 2025-03-27 (all 5 commits that day). The author (`jeiea`, 125 public repos) is active on GitHub in Sept 2026 but not on this package. Not on npm. ⇒ No npm conflict; on JSR you'd publish under your own scope anyway (e.g. `@<you>/unplugin-deno`); consider a courtesy note to jeiea.
* **Related names already in use:** `@deno/vite-plugin` (official, v2.0.4 published 2026-09-24), `jsr:@deno/esbuild-plugin`, `jsr:@deno/loader`, `denoland/deno-rolldown-plugin` (repo), `@deno-plc/vite-plugin-deno`, `@bureaudouble/deno-vite-plugin`, `@str4ngemd/deno-vite-plugin`, `@masslbs/deno-vite-plugin` (npm fork), `rspack-deno-plugin` / `@snowman/rspack-deno-plugin`, `@oazmi/esbuild-plugin-deno`, `@duesabati/esbuild-deno-plugin`. Nothing uses the `unplugin-*` naming except jeiea's JSR package. The unplugin org publishes under `unplugin-*` / `@unplugin/*`; `unplugin-deno` follows community convention (`unplugin-icons`, `unplugin-vue`, …).
* **Trademark:** Deno does not publish a naming/brand-usage policy for third-party packages (https://deno.com/brand only covers logo assets; https://deno.com/trademark is 404). The only text is the Deno Deploy Terms (`deploy/terms_and_conditions.md`): Deno trademarks are Deno's, and nothing grants a licence to use them "without our prior written permission specific for each such use". A US trademark filing for "DENO" is listed on Trademarkia (serial 90064217; owner/status not verified — the page returned 403). Practice: many packages use "deno" nominatively — `@astrojs/deno`, `@remix-run/deno`, `@sentry/deno`, `@effect/platform-deno`, `@hattip/bundler-deno`, `vercel-deno`, `deno-bin`, `@langchain/deno` — without apparent issue. **Risk: low for descriptive/nominative use** ("unplugin for Deno"), provided you (a) don't use the Deno logo/dinosaur in the package branding, (b) state "not affiliated with or endorsed by Deno Land Inc.", (c) don't use the `@deno/` scope or "official" wording. If you want certainty, ask Deno (they reply on Discord/support) — not legal advice.
* **Positioning suggestion:** "the missing *universal* Deno resolver for every bundler — what `@deno/vite-plugin` does for Vite, plus Rolldown/Rollup/esbuild/webpack/rspack/farm, plus SSR-externalize, env inlining, workspace awareness and diagnostics". Position as complementary to (and a potential engine for) Fresh's `plugins/deno.ts` and `@deno/vite-plugin`, not a replacement war with Deno's own packages; build on `@deno/loader` if it proves portable/fast (other agents to confirm).

## 8. Design implications & a demand-driven acceptance matrix

**Implications (from the evidence above, not from plugin internals):**
1. **Resolve in-process, never per-import subprocesses.** Every consumer that survived (Lume ≥3.0.6, Fresh, `@deno/esbuild-plugin`, `@deno/vite-plugin` 2.x) converged on `@deno/loader`; the `deno info` generation (deno-plc, Lockness, official v1) is where the OOM/slowness/format-breakage complaints come from.
2. **Per-environment platform + conditions** (browser vs deno/node; custom `nodeConditions`) are mandatory — Lume and Fresh both had to add them; deno-js-loader#30/#60 show condition bugs; chakra-ui/ark#3750 shows deno.json vs package.json graphs diverging.
3. **Own only what is Deno-specific, but own it early:** prefixed specifiers (`jsr:`, `npm:`, `https:`), *mapped* bare specifiers from the importer's deno.json scope (these must beat `node_modules` and native Rust resolvers — deno#33787, vite.md "import-map entries lose to node_modules"), and workspace members. Everything else (queries, virtual ids, assets, CSS) must pass through untouched.
4. **SSR is half the product.** Hono, Vike, React Router, SolidStart, TanStack Start all push server code through Vite (`ssrLoadModule`, `noExternal: true`), and Fresh's biggest bug cluster is SSR/CJS. Ship an explicit `ssr: 'externalize-to-deno' | 'bundle'` policy (+ per-package overrides) instead of inheriting whatever Vite/Rolldown do.
5. **Config-file and non-bundler resolution are adoption blockers** that no one solves (Vite 8 `--configLoader native` workaround in Fresh/Lockness; Tailwind/PostCSS/Sass can't see JSR). Even a documented helper (e.g. `unplugin-deno/register` for Node's `module.registerHooks`, or a `node_modules` materialiser for JSR aliases) would differentiate.
6. **Diagnostics are a feature:** users repeatedly ask for warnings (CJS in prod builds, node built-ins in client, missing install, min-dependency-age blocks). Fresh's `checkImports` is the only prior art.
7. **Windows + Deploy + Desktop in CI from day one** (path normalisation incl. drive-letter case; 5-min/3-GB Deploy budget; Vite running inside `deno desktop --hmr`).
